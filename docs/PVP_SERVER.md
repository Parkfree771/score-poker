# 온라인 대전(PvP) 서버 설계

> **상태: 설계만 확정. 구현은 아직 시작하지 않았다.**
> 싱글 플레이 + 토큰을 먼저 출시하고, 유저가 붙는 것을 확인한 뒤에 만든다.
> 이 문서는 그때 다시 읽기 위한 것이다.

## 0. 확정된 것

| 항목 | 결정 |
|---|---|
| 서버 | **Cloud Run** (Dart 컨테이너, 관리형) — **VM 안 씀** |
| DB | **Neon Postgres** |
| 리전 | **둘 다 도쿄** (`asia-northeast1` / `aws-ap-northeast-1`) |
| 통신 | WebSocket (JSON 메시지) |
| 비용 | 초기 사실상 0원, 사람이 붙으면 월 몇 천 원 |
| 순서 | 싱글+토큰 출시 → 그다음 PvP |

---

## 1. 왜 서버가 필요한가 (P2P가 안 되는 이유)

**히든 정보 게임이기 때문이다.**

- 손패 5장은 상대가 보면 안 된다. 클라이언트끼리 직접 통신하면 상대 손패가 그 기기에
  어떤 형태로든 도착하고, 메모리만 봐도 다 보인다.
- 덱 시드를 클라이언트가 알면 **남은 카드 순서를 전부 예측**할 수 있다.
  규칙서 §9-8이 "어떤 카드가 나갔는지 셀 수 있다"를 전략 요소로 명시한 게임인데,
  셀 필요도 없이 다 보이면 게임이 성립하지 않는다.

그래서 **서버 권위(server-authoritative)** 외에 선택지가 없다. 서버가 덱을 쥐고,
시드를 절대 내보내지 않고, 각 플레이어에게 **자기가 볼 수 있는 것만** 보낸다.

## 2. 이 프로젝트의 결정적 이점

**`lib/domain/`이 순수 Dart다.** Flutter import가 한 줄도 없다
(`card` `deck` `game` `hand` `scoring` 전부).

→ **클라이언트의 규칙 엔진을 서버에서 그대로 돌릴 수 있다.**
보통 서버 작업에서 가장 크고 버그가 많은 "규칙을 서버 언어로 재구현"을 통째로 건너뛴다.
이 이점을 지키는 것이 아래 모든 기술 선택의 제1 기준이다.

**측정치** (500판 AI 셀프플레이, 개발 PC 기준):

| 항목 | 시간 |
|---|---|
| 규칙 판정 1수 | **0.64µs** |
| 기보 리플레이로 한 판 전체 복원 | **21µs** |
| AI 한 수 계산 포함 | 26.7µs |
| 평균 턴 수 | 33.3턴 (규칙서 §10과 일치) |

즉 **서버 CPU는 병목이 아니다.** 리플레이 방식(§4)을 써도 부담이 없고,
상대가 도망갔을 때 `HeuristicAi`를 서버에서 붙이는 것도 사실상 공짜다.

## 3. 구조 — 먼저 도메인을 패키지로 뽑는다

현재 `score_poker` 패키지는 pubspec에서 Flutter에 의존한다. **순수 Dart 서버는 Flutter에
의존하는 패키지를 쓸 수 없다.** 그래서 첫 작업은 도메인 추출이다.

```
packages/score_poker_core/   ← 순수 Dart. domain/ + 프로토콜 정의
  ├ domain/     (지금 lib/domain 그대로 이동)
  └ protocol/   (클라·서버가 공유하는 메시지 타입)
lib/                         ← Flutter 앱. core를 path 의존
server/                      ← Dart 서버. core를 path 의존
```

이 한 번의 이동으로 클라와 서버가 **같은 규칙·같은 메시지 타입을 컴파일 타임에 공유**한다.
프로토콜이 어긋나면 빌드가 깨져서 알려준다.

**이 작업은 서버를 안 만들어도 손해가 아니다** — 앱 구조에도 좋고 되돌릴 일이 없다.

## 4. 핵심 설계 4가지

**(1) 서버는 완전한 상태를 들고, 클라는 시야 필터를 거친 뷰만 받는다**

```
server: GameState (양쪽 손패 + 덱 순서 전부)
   ↓ 시야 필터
p0에게: { 내 손패: [실제 카드 5장], 상대 손패: 5(개수만), 덱: 24(개수만), 필드: 전체 }
```

클라는 애니메이션용 미러만 유지하고 **합법성 판단을 하지 않는다.** UI에서 미리 막는 건
사용자 경험용일 뿐, 진짜 판정은 서버 `GameState`가 던지는 `IllegalMove`다.

**(2) 에러 코드는 `MoveError`를 그대로 쓴다**

`MoveError` 21종이 이미 정의돼 있고 `lib/ui/move_error_text.dart`에 한/영 번역이 다 있다.
서버가 enum 이름만 내려보내면 클라는 기존 코드로 그대로 표시한다. 새로 만들 게 없다.

**(3) 기보(move log)로 저장한다 — 상태 스냅샷이 아니라**

```sql
match(id, seed, p0, p1, created_at, result)
move (match_id, seq, player, action_json)
```

서버가 저장하는 건 **시드 + 수순**뿐이고, 상태는 리플레이해서 복원한다(21µs). 얻는 것:

- **재접속** — 끊겼다 들어오면 리플레이로 현재 상태 복원
- **감사 로그** — 분쟁·치팅 신고 시 판 전체 재현
- **리플레이 기능**이 사실상 공짜

`GameState`에 `toJson`을 붙일 필요조차 없다.

**(4) 선공 결정은 커밋 방식으로**

`revealForFirstTurn(index0, index1)`은 양쪽 인덱스를 한 번에 받는다. 서버가 양쪽 제출을
**둘 다 모일 때까지 보관**했다가 한 번에 호출한다. 먼저 낸 쪽의 카드는 상대에게 보내지
않는다 — 규칙서가 "동시에 공개"라고 못 박은 이유가 이것이다.
**도메인 코드 수정 없이** 서버 레이어에서 해결된다.

## 5. 토큰(결제) — 순서를 지켜야 한다

현재 지갑은 기기 로컬(`shared_preferences`)이다. **PvP에서 이걸 믿으면 루팅 기기에서
저장값만 고쳐 토큰 무한이다.** 판당 상한은 도메인이 지키지만(§`GameRules`), 보유량은
아무도 안 지킨다.

PvP에 토큰을 열려면 이 순서를 지켜야 한다:

1. **계정** — 서버 지갑은 계정이 있어야 존재한다. 익명 계정(기기 생성 키)으로 시작하고
   나중에 구글/애플 로그인 연결. (iOS에서 다른 소셜 로그인을 넣으면 Sign in with Apple도 필수)
2. **영수증 검증** — 클라가 영수증을 서버로 보내고, 서버가 Google Play Developer API /
   App Store Server API로 검증한 뒤 잔량을 올린다. 로컬 지갑은 **캐시**로 강등된다.
3. **판당 상한을 서버가 강제** — 서버의 `GameState`에 `GameRules`를 넣는다. 이미 도메인에
   구현돼 있으므로 값만 주면 된다.

**그 전까지는 PvP에서 토큰을 비활성화하고 출시한다.** 순서를 뒤집으면 첫 주에 무한 토큰이 돈다.

부수 효과: **서버 지갑이 생기면 "앱 지우면 토큰 사라짐" 문제가 같이 해결된다.**
상점의 경고문도 뗄 수 있고 환불 문의도 사라진다.

## 6. 랭킹(RP)과의 관계 — 미해결

현재 RP·티어는 **싱글 대전 결과로만** 쌓인다(`domain/records.dart`: 승 +25 / 무 +5 / 패 −15).
PvP가 열리면 두 종류의 실력 점수가 생긴다.

- PvP는 **Elo 별도 컬럼**으로 관리한다 (초반 K=32, 30판 이후 K=16).
- 규칙서 부록이 이미 "싱글 점수와 분리한다"고 명시하고 있다.
- 토큰을 PvP에서 쓰게 하는 것은 사용자가 결정했다. 공정성은 §5의 서버 판정 + 판당 1개
  상한으로 담보한다.

## 7. Cloud Run에서 WebSocket을 쓸 때의 제약 3가지

**(1) 인스턴스가 늘면 매치가 갈라진다**
같은 판의 두 플레이어가 다른 인스턴스에 붙으면 메모리의 상대 소켓을 찾을 수 없다.
→ **`max-instances=1`로 고정.** 턴제라 1 인스턴스로 동시 수백 명이 문제없다.
진짜 넘칠 때 매치 라우팅을 붙이면 되고, 그 시점이면 이미 성공한 것이다.

**(2) 과금이 "요청 시간" 기준인데 WebSocket은 판 내내 열려 있다**
무료 한도(월 200만 요청 + 18만 vCPU초)는 대략 **월 50 인스턴스-시간**에 해당한다.
동시에 여러 판이 돌수록 유리하다(인스턴스 시간은 똑같이 흐른다).
넘치면 월 몇 천 원. Apple 연 $99 앞에서는 노이즈다.
→ 정 아까우면 **수 하나당 HTTP 요청 + 폴링**으로 바꾸면 월 수만 판이 무료다.
프로토콜을 메시지로 정의해두면 **전송 계층만 갈아끼우면 되고 게임 로직은 안 건드린다.**

**(3) 요청 최대 60분 / Neon 프리는 유휴 시 컴퓨트가 잔다**
한 판이 5~10분이라 60분은 안 걸린다. Neon은 다음 쿼리가 0.5초쯤 걸리는데 판 시작할 때
한 번이라 체감이 없다.
→ **Neon에서 `LISTEN/NOTIFY`는 쓰지 말 것** (커넥션 풀링 + 자동 잠듦으로 불안정).
인스턴스가 1개면 어차피 필요 없다.

**콜드 스타트**: `min-instances=0`이면 유휴 후 첫 접속에 0.5~1.5초. 이 시점이 "상대 찾는 중"
화면이라 그 안에 숨는다. 초기에는 0으로 둔다.

## 8. 리전 (중요)

기존 Neon 프로젝트들은 **싱가포르**(`aws-ap-southeast-1`)에 있다. 한국에서 왕복 70~90ms라
이 게임에는 쓰지 말 것. **도쿄에 새 프로젝트를 판다.**

서버와 DB를 같은 리전에 붙이는 게 핵심이다 — 유저와의 왕복은 한 번뿐이지만 DB는 한
동작에 여러 번 왕복할 수 있다.

| 구간 | 시간 |
|---|---|
| 규칙 판정 | 0.001ms |
| DB 기록 (같은 리전) | 1~2ms |
| **네트워크 왕복 (한국↔도쿄)** | **30~40ms** |
| 합계 | **약 40ms** |

전체 지연의 99%가 네트워크다. 사람이 느리다고 인지하는 경계가 100ms 부근이라 40ms는
즉시 반응으로 느껴진다.

## 9. 그 외 빠지면 안 되는 것

- **턴 타이머** — 30초, 초과 시 자동 폴드. 없으면 지고 있는 쪽이 앱을 안 끄고 버틴다.
- **재접속 유예** — 60초, 그 안에 못 오면 패배 처리.
- **봇 대체** — 큐가 비었거나 상대가 도망가면 `HeuristicAi`를 서버에서 붙인다.
- **진짜 느려지는 원인은 상대 네트워크다.** 지하철에서 상대가 멈추면 내 화면도 멈춘다.
  어떤 서버로도 못 고치고, 턴 타이머로 처리하는 게 표준이다.

## 10. 탈락시킨 대안

| 대안 | 탈락 이유 |
|---|---|
| Firebase / Supabase 리얼타임 | 규칙 판정을 못 한다. Cloud Functions(TS)에 규칙을 다시 짜야 하고, 그러면 규칙이 두 벌이 되어 영원히 어긋난다 |
| Nakama · Colyseus | 같은 이유(Go/JS) |
| **Cloudflare Durable Objects** | 구조적으로는 **가장 이상적**이다(판 하나 = 객체 하나, WebSocket 직접 처리, 유휴 시 hibernate, §7의 제약 1·2가 없음). 그러나 JS/TS 전용이라 §2의 이점이 날아간다. 규칙이 두 벌이 되면 "상대는 두는데 나는 못 두는" 버그가 나오고 유저는 그걸 치팅으로 오해한다 |
| VM 직접 운영 | 사용자가 명시적으로 거부 |

## 11. 단계

| 단계 | 내용 | 끝나면 |
|---|---|---|
| 1 | 도메인 → `score_poker_core` 추출, 서버 스켈레톤, 로컬에서 클라 2개로 대전 | 인증 없이 대전이 된다 |
| 2 | 계정 + 매치메이킹 + Elo + 기보 저장 | 랭킹 있는 PvP |
| 3 | 서버 지갑 + 영수증 검증 | **PvP에 토큰 개방** |
| 4 | 턴 타이머·재접속·이탈 처리, 배포 | 출시 가능 |

1단계가 전체의 절반쯤 된다.
