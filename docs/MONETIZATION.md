# 수익화(결제) 설계

> 현재 상태: **상점 · 지갑 · 상품 · 인게임 사용까지 구현 완료.** 남은 것은 스토어 SDK 연결(§6).
> 지금 상태로 웹/데스크톱에서 상점 화면이 그대로 열리고(참고가 표시), 게임 안에서 토큰도
> 쓸 수 있다. SDK가 준비되면 `PurchaseService` 구현체만 갈아끼운다.
>
> 온라인 대전과의 관계는 `PVP_SERVER.md`.

## 0. 광고는 없다 (결정 기록)

이전 설계에는 배너·전면 광고와 "광고 제거" 상품이 있었다. **전부 들어냈다.**
카드 게임은 한 판이 30턴 넘게 이어지는 집중형 플레이라 어디에 광고를 넣어도 흐름을 끊는다.
`ad_service.dart` / `ad_slot.dart` / `entitlements.dart` / `remove_ads` 상품은 삭제됐다.

**대가**: 무과금 사용자에게서 나오는 매출이 0이 된다. 매출은 전적으로 토큰 판매에 달렸고,
그래서 §4의 무료 지급량 조정이 이 게임에서 가장 민감한 숫자가 됐다.

## 1. 무엇을 파는가

인게임 토큰 **두 종류뿐**이다.

| 토큰 | 효과 | 규칙상 카운터 |
|---|---|---|
| **쉴드 토큰** | 내 필드의 카드 1장을 쉴드로 만든다 | 조커(덱에 2장) — 쉴드를 깨는 유일한 수단 |
| **공격 토큰** | 손패의 카드 1장에 공격 표식을 붙인다(덱에서 뽑은 카드도 공격 가능) | 같은 숫자 규칙 + 내 빈 칸 필요 + 상대 쉴드 |

둘 다 `RULES.md`에 이미 존재하는 정식 메커닉이다. 새 규칙을 만든 게 아니라, **규칙이 이미
제한해 둔 자원(공격 표식 5장, 조커 2장)을 한 번 더 쓰게 해 주는 것**이다.

구현 위치: `GameState.declareShield()` / `GameState.markAttacker()`
(규칙은 `test/token_rules_test.dart`, 화면 흐름은 `test/token_ui_test.dart`가 고정한다)

**두 행동 모두 턴을 소모하지 않는다.** 비용은 토큰이지 한 턴이 아니다 — 턴까지 먹으면
쓸 이유가 없어져서, 팔아도 아무도 안 쓰는 아이템이 된다.

### 왜 pay-to-win이 아닌가

**한 판에 종류별 1개까지만 쓸 수 있다.** (`GameRules`, 도메인에서 강제)

100개를 산 사람이 한 판에서 얻는 이득은 1개 쓴 사람과 **정확히 같다.** 돈이 늘리는 것은
이득의 크기가 아니라 "이득을 쓸 수 있는 판의 수"뿐이다. 이 상한이 밸런스의 전부이므로
**절대 완화하지 말 것** — 여기가 풀리는 순간 랭킹이 무의미해진다.

상한을 **UI가 아니라 도메인**에 둔 이유도 같다. UI에서만 막으면 뚫린다. 온라인 대전에서는
서버가 같은 엔진을 돌려 판정하므로(→ `PVP_SERVER.md`), 상한이 규칙 엔진 안에 있어야
클라이언트를 조작해도 소용이 없다.

**사용하려면 두 관문을 모두 통과해야 한다:**

| 관문 | 지키는 것 | 어디에 |
|---|---|---|
| 판당 상한 | "한 판에 1개" | `GameRules` (도메인) |
| 보유량 | "가진 만큼만" | `TokenWallet` (지갑) |

이 둘이 분리돼 있어야 도메인이 결제를 모르는 상태로 남는다.

### 팔지 않는 것

힌트 · 되돌리기 · 추가 조커 · 유리한 시작 패 · 레이팅 보호 · 유리한 매칭.
전부 상한을 둘 수 없거나 정보 우위를 파는 것이라 위의 논리가 성립하지 않는다.

### ⚠️ 미해결: 랭킹(RP)과의 관계

현재 RP·티어는 **싱글 대전 결과로만** 쌓인다(`domain/records.dart`: 승 +25 / 무 +5 / 패 −15).
토큰을 싱글에서 쓰면 그대로 RP에 반영된다.

사용자 결정: **싱글과 온라인 대전 양쪽에서 토큰을 쓸 수 있게 한다.** 공정성은 판당 1개
상한과, PvP에서는 서버 판정으로 담보한다. 자세한 내용은 `PVP_SERVER.md` §5·§6.

**PvP 출시 전까지 남은 숙제**: 로컬 지갑은 위조 가능하므로(루팅 기기에서 저장값 수정)
서버 지갑 + 영수증 검증이 끝나기 전에는 PvP에서 토큰을 비활성화해야 한다.

## 2. 상품 구성과 가격

| 상품 ID | 내용 | 참고가(KRW) | 개당 |
|---|---|---|---|
| `token_set_20` | 쉴드 10 + 공격 10 | 4,990 | 249.5 |
| `token_shield_10` | 쉴드 10 | 3,300 | 330 |
| `token_attack_10` | 공격 10 | 3,300 | 330 |

- **공격과 쉴드는 같은 가격.** 둘의 강도가 대칭이므로 가격도 대칭이다(테스트로 고정).
- **세트가 낱개 두 개(6,600원)보다 1,610원 싸다 → 24% 할인.** 낱개 두 개는 사실상 앵커고,
  실제로 팔리는 것은 세트다. 세트가 더 싸다는 조건도 테스트로 고정돼 있다.
- 한 판에 최대 2개(각 1개) 쓰므로 **부스트 1판당 실질 비용은 세트 기준 약 499원.**

**실수령액**: 한국은 스토어 표시가가 부가세 포함이다. 4,990원 → 부가세 제외 약 4,536원 →
스토어 수수료 15%(연 매출 100만 달러 이하 소규모 개발자 프로그램) 차감 후 **약 3,856원.**
수수료 30% 구간이면 약 3,175원.

**주의 — 애플 가격 포인트**: App Store는 정해진 가격 포인트 중에서만 고를 수 있어
`₩3,300`·`₩4,990`이 그대로 없을 수 있다(구글은 임의 금액 지정 가능). 플랫폼마다 실제 금액이
갈릴 수 있으므로 **가격은 절대 앱에 하드코딩하지 않는다** — 할인율 배지까지 스토어가 준
`rawPrice`로 계산한다(`discountPercent()`). 등록 전에 App Store Connect에서 실제 사용 가능한
포인트를 확인할 것.

`referencePriceKrw`는 **개발/웹 미리보기 전용**이다. 실기기에서는 쓰이지 않는다.

## 3. 무료 지급 (`TokenGrantPolicy`)

| 시점 | 지급 |
|---|---|
| 첫 실행 1회 | 쉴드 3 + 공격 3 |
| 매일 1회 | 쉴드 1 + 공격 1 |

근거:
- **환영 지급**: 써 본 적 없는 아이템은 아무도 사지 않는다. 첫 판부터 효과를 경험시킨다.
- **데일리**: 하루 한 판을 부스트할 수 있다. 하루 1~2판 하는 라이트 유저는 사실상 전부
  무료로 덮이고(어차피 결제하지 않을 층이다), 하루 5판 이상 하는 층에게만 "부족하다"는
  감각이 생긴다. **이 층이 결제 모수다.**

광고가 없으므로 이 숫자가 매출을 직접 결정한다. 출시 후 가장 먼저 조정하게 될 값이라
`TokenGrantPolicy` **한 곳에만** 둔다.

## 4. 구조

```
lib/monetization/
  tokens.dart          TokenKind(쉴드/공격) + 저장 키
  products.dart        상품 정의 · ProductOffer · 할인율 계산
  wallet.dart          TokenWallet(잔량·지급·소모·데일리) + 지급 정책
  wallet_store.dart    로컬 저장(shared_preferences) + 중복 지급 방지 기록
  purchase_service.dart 결제 인터페이스 + 스텁
  monetization.dart    조립체 + MonetizationScope(InheritedWidget)
lib/ui/shop_screen.dart 상점 화면(잔량 · 데일리 · 상품)
```

쓰는 법:

```dart
final m = MonetizationScope.of(context);
m.wallet.balanceOf(TokenKind.shield);   // 잔량
await m.wallet.spend(TokenKind.shield); // 인게임에서 사용 (false면 상점으로 유도)
await m.wallet.claimDaily();            // 데일리 무료 지급
await m.buy(Products.set20);            // 상점에서 구매
```

## 5. 지켜야 할 규칙 (`test/monetization_test.dart`로 고정)

1. **도메인(`lib/domain`)은 결제를 모른다.** 토큰의 효과는 `GameRules`라는 순수한 값으로만
   도메인에 들어간다. 게임 규칙이 결제에 의존하면 테스트가 어려워지고 pay-to-win으로 흐른다.
2. **지급 순서는 `지급 → 저장 → 완료`.** 완료를 먼저 부르고 앱이 죽으면 돈만 받고 토큰을
   못 주는 창이 생긴다.
3. **같은 구매 id로는 두 번 지급하지 않는다.** 스토어는 `completePurchase` 전까지 같은
   구매를 계속 재배달한다. `deliveredPurchaseIds`가 이걸 막고, 재시작 후에도 유지된다.
4. **이미 지급한 구매여도 완료 처리는 반드시 다시 한다.** 안 하면 영원히 재배달되고,
   안드로이드에서는 **그 상품을 다시 살 수 없게 된다**(가장 흔한 결제 버그).
5. **배달 스트림 구독은 `initialize()` 보다 먼저.** 밀려 있던 구매가 연결 즉시 흘러온다.
6. **동시에 온 구매는 직렬화해서 처리한다.** 둘이 같은 잔량을 읽으면 한 건이 사라진다.
7. **가격·할인율은 스토어가 준 값으로만.** 하드코딩한 할인율은 다른 나라에서 거짓 표시가
   되고 스토어 정책 위반이다. 계산할 수 없으면 배지를 숨긴다.
8. **잔량은 음수가 되지 않고, 저장값이 깨져도 앱은 켜진다.**

## 6. 실제 SDK를 붙일 때 (아직 안 됨 — 선행 조건 있음)

**선행 조건**

1. **android/ios 플랫폼 폴더가 없다.** 먼저:
   `flutter create . --platforms=android,ios --org <역방향 도메인>`
   → 번들 ID는 스토어 등록 후 변경 불가. 먼저 정할 것.
2. **Windows 개발자 모드가 꺼져 있다.** 결제는 플러그인이라 `flutter pub get`이 심볼릭
   링크를 만든다. 꺼져 있으면 실패한다 → `start ms-settings:developers`
3. 스토어 계정: Google Play Console(개발자 등록 1회) / App Store Connect(연간 + Mac·Xcode 필수).
   **상품 ID를 `products.dart`와 글자 하나까지 똑같이** 등록한다. 세 상품 모두 **소비성**으로.

**교체 지점**

| 인터페이스 | 실제 구현 |
|---|---|
| `PurchaseService` | `in_app_purchase`를 감싼 `StorePurchaseService` |

구현 시 주의:
- `purchaseStream`의 `PurchaseStatus.purchased`/`restored`만 `delivered`로 흘린다.
  `pending`은 **지급하지 않는다**(승인 전 결제).
- `complete()`는 iOS `completePurchase` + **안드로이드 소비 처리**를 모두 한다.
- `purchaseId`는 `PurchaseDetails.purchaseID`를 쓴다(중복 지급 방지 키).
- 웹/데스크톱은 계속 `StubPurchaseService`(`kIsWeb`/`Platform`으로 분기).

**심사 관련**
- 상품이 전부 소비성이라 **"구매 복원" 버튼은 필수가 아니다**(비소비성·구독이 있을 때만 요구).
  대신 §7의 서버 저장이 없으면 재설치 시 잔량이 사라진다는 사실을 상점에 표시해야 한다
  (지금 표시하고 있다).
- Play 데이터 세이프티 / App Privacy 신고서에 결제 관련 항목을 채운다.

  AI라 사람의 상한과는 다를 수 있음. 상점 문구에서 "승리 보장" 류 표현을 쓰지 않을
  근거이기도 하다. 재측정: `dart run tool/balance_sim.dart`.
- **영수증 검증(서버)** — 지금은 클라이언트만 믿는다. 루팅 기기에서 저장값을 고치면 토큰을
  늘릴 수 있다. 싱글에서는 자기 손해라 무시 가능하지만, **PvP는 서버가 토큰 사용을
  판정해야 한다.** 클라이언트 잔량을 믿고 PvP를 열면 안 된다.
- **계정 연동** — 소비성 잔량은 복원되지 않는다. 재설치·기기 변경 시 사라지고, 이건 환불
  문의로 돌아온다. 서버 지갑이 근본 해결책이다.
- 스토어 등록 정보(가격 포인트 확인, 세금 카테고리, 상품 설명·스크린샷).

## 8. 인게임 사용 흐름 (구현 완료)

게임 화면 손패 옆 액션 묶음: `[쉴드][표식] / [이모트][폴드]` (세로는 2×2, 가로는 한 줄).

1. 토큰 버튼을 누르면 **대상 지정 모드**로 들어간다(쉴드 = 내 필드 카드 탭 / 표식 = 손패 탭).
2. **보유 확인 → 규칙 적용 → 차감** 순서로 처리한다.
   차감을 먼저 하면 규칙 위반으로 튕겼을 때 토큰만 사라진다 → 환불 문의가 된다.
3. 토큰이 없으면 스낵바에 **상점 바로가기**를 띄운다. 게임을 끊지 않는 선에서의 유일한
   판매 접점이다(광고가 없으므로 여기가 유일한 전환 지점이기도 하다).
4. `MonetizationScope`가 없는 환경(위젯 테스트·스크린샷)에서는 토큰 버튼을 아예 그리지
   않는다 — 기존 골든이 깨지지 않는다.

**주의**: `MonetizationScope`는 `MaterialApp`보다 **위**에 있어야 한다. 아래에 두면
`Navigator.push`로 연 상점 화면이 스코프 밖으로 나가 즉시 죽는다.
